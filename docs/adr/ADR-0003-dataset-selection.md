# ADR-0003 — dunnhumby Complete Journey as seed, synthetic amplifier for scale

**Status:** Accepted · **Date:** 2026-08-06 · **Reversal cost:** Medium

---

## Context

The dataset determines whether the architecture is credible. A toy dataset makes every downstream
decision arbitrary: you cannot justify liquid clustering, skew handling, or SCD Type 2 against data
that has no cardinality, no history, and no dimensional churn.

Requirements for the dataset:

1. **Genuine business semantics** — a reviewer must be able to ask "what is this number for?" and
   get an answer that isn't circular.
2. **Relational depth** — multiple entities with real foreign keys, so joins are meaningful and
   dimension modelling has something to model.
3. **Temporal depth** — enough history for cohort behaviour, seasonality, and a train/validation
   split that isn't leakage.
4. **Dimensional churn** — entities whose attributes change over time, so SCD Type 2 is a
   requirement rather than a demo.
5. **Permissive licence** — publishable in a public repository.
6. **Domain relevance** — grocery retail, matching the reviewer's working context.

## Options considered

### A. A "big data" public dataset (NYC taxi, GitHub events, Common Crawl)
Large enough to make Spark work hard.

**Rejected.** Volume without business meaning. There is no dimension to slowly change, no campaign
to attribute, no household to churn. Every gold table would be an invented aggregate, and the
model at the end would be a regression with no stakeholder. These datasets prove you can run Spark;
they cannot prove you can model a business.

### B. basedosdados.org (Brazilian public data)
High quality, genuinely large, well curated.

**Rejected for the core** — though see the revisit trigger. The retail-adjacent tables (IBGE
monthly commerce survey, PNAD, RAIS) are *aggregated*, not transactional. No basket, no SKU, no
household. You cannot build a propensity model or a coupon-targeting decision on top of a monthly
index. The relevance to the reviewer's day job (US grocery, basket-level) is also weak.

### C. Databricks sample datasets (`samples.tpch`, `samples.nyctaxi`)
Zero setup.

**Rejected.** Every Databricks portfolio uses them. Using them signals that the dataset was chosen
for convenience, which invites the reviewer to assume the architecture was too.

### D. Fully synthetic data
Total control over every stress scenario.

**Rejected as the sole source.** Synthetic data has synthetic correlations. A churn model trained
on data generated by a rule you wrote will recover the rule you wrote — an impressive-looking
metric that means nothing. The model layer would be theatre.

### E. dunnhumby *The Complete Journey* as seed + synthetic amplifier ✅

**Chosen.**

- **Provenance:** dunnhumby is the customer-data science company owned by (and built around) a
  major US grocery retailer. The dataset is the retail industry's canonical open basket dataset.
- **Content:** ~2 years, 2,500 households, 8 relational tables — `transaction_data`, `product`,
  `hh_demographic`, `campaign_desc`, `campaign_table`, `coupon`, `coupon_redempt`, `causal_data`.
  Basket-level line items with quantity, sales value, retail discount, coupon discount, store,
  and time-of-day; plus promotion exposure (display / mailer) per product per store per week.
- **Licence:** CC BY 4.0 via Mendeley Data (DOI `10.17632/7myy93ym6k.1`). Attribution required and
  given in `data/README.md`.
- **Fit:** it natively contains D1 (coupon targeting), D2 (household lapse), and D3 (promotion
  performance) from the North Star. The decisions were not invented to fit the data.

## Decision

**Two-tier dataset strategy.**

**Tier 1 — Seed (real).** The dunnhumby tables are the source of truth for *distributions and
semantics*: basket size distribution, department mix, price points, discount depth, promotion
response, household demographics, day-of-week and time-of-day shape.

**Tier 2 — Amplifier (synthetic, distribution-preserving).** `generator/` resamples the seed to
produce a continuous event stream at arbitrary volume, preserving the empirical joint
distributions rather than inventing them. It emits to two sources:

- **Event landing zone** (JSON to a Unity Catalog Volume) — basket line events, consumed by Auto
  Loader. This is the D3/D4 real-time path.
- **Lakebase Postgres** — slowly-changing masters (`product`, `store`, `household`), mutated on a
  schedule to generate genuine CDC traffic and SCD Type 2 history.

### Why the amplifier is honest, not a cheat

The distinction that matters: the amplifier **resamples** the seed's empirical distributions; it
does not **generate** behaviour from a rule. Household *h*'s next basket is drawn from the observed
basket distribution conditioned on that household's real demographic and historical department mix.
No latent generating function is invented, so no model can recover one.

The one place synthetic structure *is* deliberately injected is the stress scenarios, and each is
labelled, configurable, and off by default:

| Scenario | Config key | Effect |
|---|---|---|
| Store skew | `skew.store_concentration` | 0.5% of stores receive ~40% of baskets |
| Small files | `stream.trigger_seconds` | Sub-MB files at high frequency |
| Late arrival | `stream.late_pct` / `stream.late_max_lag` | 3% of events lag up to 6h |
| Schema drift | `drift.at_event` | Column added + renamed at a fixed event offset |
| Duplicate delivery | `cdc.replay_window` | CDC source replays a window |

**Any model trained on amplified data is evaluated on the real seed's held-out period, never on
synthetic rows.** This is enforced in `src/retail_lakehouse/ml/` and asserted in the ML test suite.
Without that rule the whole ML layer would be self-congratulatory.

### The relative-date problem

`transaction_data.DAY` is an integer 1–711 with no calendar anchor, and `TRANS_TIME` is an `HHMM`
integer. This is a modelling decision, not a formatting one: anchoring `DAY = 1` to a chosen
calendar date fabricates seasonality alignment (a synthetic "December" that was not December).

Decision: anchor `DAY = 1` to a Monday so day-of-week structure — which *is* real in the data —
survives, and treat month/holiday effects as **unavailable**. Any feature or dashboard implying
calendar seasonality is prohibited, and a test asserts no feature named `month`/`quarter`/`holiday`
enters the feature set. Recording this prevents a future contributor from "fixing" the anchor and
silently introducing a fake seasonal signal.

## Consequences

**Positive**
- The business layer is defensible end to end; every gold metric maps to a decision with an owner.
- Stress scenarios are reproducible and parameterised, so "we handled skew" is demonstrable with a
  before/after query profile rather than asserted.
- Volume is a knob, so the same code runs on a laptop (unit tests, 1k events) and at scale.

**Negative**
- The seed is small (2,500 households). Any claim about *absolute* scale must be qualified as
  amplified. All performance evidence in this repo states its input volume explicitly.
- Amplified data cannot support claims about model generalisation to new households.
- Calendar seasonality is permanently unavailable. A real retail platform would care about it a
  great deal; this one cannot, and says so.

## Reversal cost: Medium

Swapping the seed means rewriting bronze schemas, silver conformance, and the generator's
distribution fitting — roughly the ingestion half of the project. Gold, ML, and the agentic layer
survive if the conformed silver model is kept stable, which is an argument for keeping silver's
entity model deliberately generic (`fact_basket_line`, `dim_product`, `dim_household`, `dim_store`)
rather than dunnhumby-shaped.

## Revisit trigger

Add basedosdados as a **conformed external dimension** (regional income, inflation deflator) if the
promotion-elasticity work in D3 needs a macro control variable. That is additive and does not
disturb the core — which is exactly why it was rejected as a *core* source but kept as a candidate
extension.
